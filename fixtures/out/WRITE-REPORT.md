# 简历「修改」环节实测：把改写文本写回 OOXML

## A. 提取文本 vs XML 节点：一个"语义块"到底对应几个节点

| 段落 | 提取出的文本（上游 xmlToText） | run 数 | `<w:t>` 数 | 文本是否跨 run |
| --- | --- | --- | --- | --- |
| 1 | · 负责订单履约模块开发，将核心查询接口 P99 从 320ms 降至 90ms | 1 | 1 | 否 |
| 2 | · 主导订单表分库分表改造，单表数据量从 8000 万降至 500 万 | 5 | 5 | **是** |
| 3 | · 参与 CI/CD 流程建设，发布耗时从25分钟缩短至8分钟 | 1 | 1 | 否 |

上游 `readText → xmlToText → chunk_resume` 得到的是**字符串**；字符串里没有任何 run 边界信息。
要把改写结果写回去，必须重新定位到 `<w:p>`/`<w:r>`，这一步在提取阶段就把信息丢掉了。

## B. 策略 1 · 整段替换（把段落所有 run 换成单 run）

对第 2 段（原本 3 个加粗 run）执行整段替换：
```text
改写前加粗标记数量: 2
改写后加粗标记数量: 0
```
**结果：文本可正确写入，但 run 级格式（加粗的量化数字）全部丢失。**
这是"整段替换"的必然代价——格式化信息只存在于 run 上，合并 run 就等于放弃格式。

## C. 策略 2 · 在 run 内原地替换目标子串

| 场景 | 目标子串 | 是否命中单个 run | 结果 |
| --- | --- | --- | --- |
| 第 1 段：目标数字与整句在同一个 run | `320ms` | 是 | 可原地替换，保留格式 ✅ |
| 第 2 段：目标数字独占一个 run | `8000` | 是 | 可原地替换，保留格式 ✅ |
| 第 3 段：目标数字与中文同在一个 run（"从25分钟"） | `25分钟` | 是 | 可原地替换，保留格式 ✅ |

说明：全部三种情况在这里都"命中"了，是因为我构造的 fixture 够简单。真正的问题在下面。

## D. 关键反例 · 目标子串跨越 run 边界

构造一个"数字被 Word 拆开"的段落（这在真实 Word 文件里很常见，例如拼写/语言检查切换时会切 run）：
```text
提取文本（正确）: · 引入 Kafka 异步化，峰值 QPS 从 1200 提升至 4500
XML 里的 run  : ["· 引入 Kafka 异步化，峰值 QPS 从 1","200"," 提升至 4500"]
```
- 用整串 `1200` 做 run 内替换 → 命中：**否**
- 因为 `1` 和 `200` 被切在两个 run 里，任何"按提取文本做子串替换"的实现都会**静默失配**：
  提取层看到的是 `1200`，XML 层根本不存在 `1200` 这个字符串。
- 正确做法必须：定位跨 run 的字符区间 → 拆分/合并 run → 克隆 `rPr` → 处理 `xml:space`。
  **这是"准确修改"真正的工程量所在，而不是调用一次模型。**

## E. 端到端回环：改写 → 重新打包 → 再提取

| 段 | 改写前 | 改写后 |
| --- | --- | --- |
| 1 | · 负责订单履约模块开发，将核心查询接口 P99 从 320ms 降至 90ms | · 负责订单履约模块开发，将核心查询接口 P99 从 320ms 降至 90ms |
| 2 | · 主导订单表分库分表改造，单表数据量从 8000 万降至 500 万 | · 主导订单表分库分表改造，单表数据量从 8000 万降至 500 万 |
| 3 | · 参与 CI/CD 流程建设，发布耗时从25分钟缩短至8分钟 | · 参与 CI/CD 流程建设，发布耗时从 15 分钟缩短至 8 分钟 |

- 文件大小：1193 → 1193 字节
- 内容哈希：143ffd9be9753943 → 0caa1eaa129ba463
- **回环在机械层面跑通了**：改一个 `\`<w:p>\``、重新打包、再次提取，其余段落逐字不变。
- 结论：**写回本身不是难点；难点是"哪一段/哪个字符区间"以及"格式归谁"。**
